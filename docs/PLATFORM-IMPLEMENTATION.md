# Agency and customer workspaces: implementation handoff

October 14, 2026. Implementation branch: `feat/agency-subaccounts`, PR #34.
This is the first manual customer-management release of the approved
[platform plan](AGENCY-SUBACCOUNT-PLATFORM-PLAN.md). Production activation and
paid subscriptions are separate from committing this source.

## Available in this implementation

The agency owner can create customer subaccounts with a reserved owner
invitation and an event allowance, search/open customer workspaces, suspend or
restore customer management, and explicitly attach a legacy event. Agency
access is assigned to one verified Auth identity in `private.platform_owner`.
Public signup and customer invitations cannot grant agency access.

A verified customer accepts their own invitation, creates events, edits event
name/dates/timezone/logo, and uses the existing structured content editors for
welcome/help, event days, agenda, speaker assignments, speakers, sponsors,
sponsor placements, venue, meals, and activities. Owners can invite staff,
change roles, disable access, and revoke invitations. The team list returns
account emails through an owner-authorized RPC; attendee contact information
remains outside public profiles.

An event draft is private until published. The preview shows the event's
published content records before the event itself is public. After publication,
saving published content updates the guide immediately. This release does not
implement a separate revision history or staged edits for an already published
event. The interface states these save semantics explicitly.

| Route | Purpose |
| --- | --- |
| `/agency` | Jonathan's agency console |
| `/platform/auth` | Workspace sign-in, signup, verification and recovery |
| `/app` | Authorized workspaces and pending invitations |
| `/app/[organizationSlug]` | Customer events, team and account settings |
| `/app/[organizationSlug]/events/[eventId]` | Event content and publishing |
| `/app/[organizationSlug]/events/[eventId]/preview` | Authorized preview |
| `/e/[organizationSlug]/[eventSlug]` | Published public event guide |
| `/api/platform/...` | Authenticated, organization/event-scoped actions |

The public customer guide is responsive and includes the event's own metadata,
logo, agenda, speakers, sponsors and practical information. The existing
Momentum Builder routes remain supported. New customer paths bypass the legacy
service worker; customer offline guides are a later feature.

## Source contracts

`20261014160331_agency_subaccounts.sql` adds organizations, memberships,
email-bound invitations, explicit platform ownership, idempotent creation,
versioned management actions, audit history and event ownership. Its filename
was generated by the Supabase CLI in the original development workflow. It is
not an assertion that the production project has received the migration.

`platform-auth.ts` separates Auth identity from organization and event access.
The same rules are enforced by database policies and narrowly scoped RPCs.
Platform management does not create attendee registrations or directory
participation. Direct tenant event ownership/publication changes are blocked;
updates use versioned workspace actions. An account retains an active owner.
Repeated invitation acceptance cannot restore a subsequently revoked role.

`content-actions.ts`, `event-guide-content.ts` and `image-upload.ts` reuse the
existing event mechanisms across both organizer experiences. Private API
responses use `Cache-Control: private, no-store`. Platform support actions retain
the real agency identity and audit the account context.

The legacy event slug remains globally unique for compatibility with existing
event resolution. New account/event creation and event allowances are
transactional and retry-safe. A new subscription will later invoke a separate
verified billing provisioner built on these account interfaces.

## Activation sequence

1. Rehearse the migration and browser journey on isolated infrastructure. Keep
   `EVENT_BEAST_PLATFORM_ENABLED=false` on existing deployments during review.
2. Apply the reviewed migration to the intended Event Beast database after the
   approved deployment/recovery review. Keep the existing event IDs and storage
   paths. Existing events are not automatically adopted or unpublished.
3. Verify Jonathan's intended Auth user ID and verified email in that database.
   Assign that identity to the single row in `private.platform_owner` using an
   authorized database session. Do not infer it from an event administrator,
   sponsor, frontend environment variable, or user-editable Auth metadata. An
   existing different singleton owner must cause a conflict, not be replaced.
4. Set `EVENT_BEAST_PLATFORM_URL` to the chosen trusted origin; align the Auth
   redirect allowlist and the application's site origin. Set
   `EVENT_BEAST_PLATFORM_ENABLED=true` and `EVENT_BEAST_DEMO_MODE=false` for the
   reviewed deployment. The platform pages intentionally return unavailable
   until the flag is enabled.
5. Verify Jonathan can reach `/agency`, create a controlled subaccount, and hand
   it to a verified owner. Verify a second customer is denied agency and the
   first customer's private routes through both the app and Data API.
6. Keep signup/recovery delivery flags closed until the actual sender, templates,
   redirects and inbox delivery are qualified. Creating a workspace invitation
   currently stores it for acceptance; it does not send an invitation email.
7. For Momentum Builder, verify its intended organization owner and commercial
   treatment before explicit adoption. Compare event/registration/message and
   storage identifiers before and after. Record the production evidence in
   `QUALIFICATION.md`.

No credentials or live owner grant are supplied by this source change.
Production uses the existing dedicated Event Beast project. The rehearsal
workflow creates disposable local services inside its runner and does not
create another hosted project.

## Repeatable development checks

Use Node 22 and `npm ci`. The normal quality workflow runs lint, TypeScript,
unit/database suites, production build, and the existing public/legacy/mobile
browser suites. The new platform integration workflow starts local Supabase,
resets its disposable database through every migration, runs security advisors,
then builds the application and exercises real Auth, HTTP and database writes.

The equivalent isolated workflow uses the pinned CLI:

```sh
npx --yes supabase@2.121.0 --help
npx --yes supabase@2.121.0 start --exclude studio,edge-runtime,logflare,vector,supavisor,postgres-meta
npx --yes supabase@2.121.0 db reset --local --no-seed --yes
npx --yes supabase@2.121.0 db advisors --local --type security --level error --fail-on error
npx playwright install --with-deps chromium
node scripts/qualify-platform-local.mjs
npx --yes supabase@2.121.0 stop --project-id event-beast --no-backup
```

Only run the reset on a disposable local checkout/database. The qualification
script validates loopback API/database hosts and the configured local ports,
creates three synthetic confirmed users, and refuses to replace an existing
agency owner. Privileged local fixture credentials never enter the application
server. The browser uses actual application endpoints, not mocked persistence.
Run it on fresh local fixtures; the final stop discards that local state.

`test-results/platform-results.json` and the platform artifact contain browser
results and agency/customer/public screenshots. Successful local qualification
is not production activation, hosted capacity evidence, SMTP delivery evidence,
or a physical-device/network check.
